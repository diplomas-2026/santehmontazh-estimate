# Техническая спецификация

## 1. Название проекта

Информационная система для расчета сметы и закупки материалов для объекта ООО «САНТЕХМОНТАЖ».

## 2. Цель продукта

Продукт предназначен для автоматизации подготовки сметы на объект, расчета потребности в материалах, формирования закупочных позиций и контроля перехода материалов от стадии расчета к закупке.

Система должна сократить ручные ошибки, ускорить расчет сметы, обеспечить прозрачность плановых затрат и разделить ответственность между сметчиком, снабженцем и руководителем.

## 3. Основные бизнес-проблемы

- Расчет сметы и потребности в материалах выполняется вручную или в разрозненных таблицах.
- Сложно отследить, какие материалы уже заложены в смету, а какие реально отправлены в закупку.
- Нет единого статуса объекта, сметы и закупки.
- Руководителю неудобно контролировать плановую стоимость и отклонения.

## 4. Целевая аудитория

- Сметчик
- Снабженец
- Руководитель проекта
- Администратор системы

## 5. Границы MVP

В первую версию входят:

- ведение объектов;
- ведение справочника материалов;
- ведение справочника поставщиков;
- создание сметы по объекту;
- хранение версий сметы и сравнение версий;
- добавление сметных позиций с автоматическим расчетом сумм;
- автоматическое агрегирование потребности по материалам;
- формирование заявок на закупку на основании сметы;
- сравнение предложений поставщиков по закупочным позициям;
- изменение статусов закупки;
- согласование закупки с комментариями;
- сравнение плановой и фактической стоимости;
- журнал действий пользователей;
- экспорт сметы и закупки в печатную форму;
- просмотр сводных показателей по объекту;
- разграничение доступа по ролям;
- seed-данные и тестовые пользователи;
- API + Web UI + Playwright E2E.

В MVP не входят:

- интеграция с 1С;
- импорт из Excel;
- учет фактических складских остатков;
- многовалютность;
- электронное согласование документов;
- уведомления по email или мессенджерам;
- OCR и распознавание счетов;
- автоматическая интеграция с внешними маркетплейсами поставщиков.

## 6. Роли и модель авторизации

Выбирается role-based модель, так как для дипломного проекта она лучше всего объяснима, прозрачно тестируется и одинаково реализуется в API и Web.

### 6.1. Роли

#### `ADMIN`

Права:

- управление пользователями;
- полный доступ ко всем объектам, сметам, материалам и закупкам;
- изменение любых статусов;
- просмотр административной страницы.

#### `ESTIMATOR`

Права:

- просмотр объектов и материалов;
- создание и редактирование смет;
- добавление, редактирование и удаление сметных позиций, пока смета не отправлена в закупку;
- просмотр агрегированной потребности по материалам;
- перевод сметы в статус `READY_FOR_PURCHASE`.

Ограничения:

- нет доступа к управлению пользователями;
- нет права создавать закупки и менять закупочные статусы.

#### `PURCHASER`

Права:

- просмотр объектов, материалов и смет;
- создание заявок на закупку на основе сметы со статусом `READY_FOR_PURCHASE`;
- редактирование закупочных позиций;
- перевод закупки по рабочим статусам;
- фиксация закупленной цены и количества.

Ограничения:

- нет доступа к управлению пользователями;
- нет права редактировать сметные позиции.

#### `MANAGER`

Права:

- просмотр всех объектов, смет, закупок и аналитики;
- изменение статуса объекта на завершающих этапах;
- утверждение закупки.

Ограничения:

- только чтение по материалам, сметам и позициям;
- нет доступа к управлению пользователями.

### 6.2. Правила доступа

- Доступ в систему только для аутентифицированных пользователей по JWT.
- Все защищенные API требуют `Authorization: Bearer <token>`.
- UI скрывает недоступные разделы меню и действия.
- Backend является источником истины по правам и возвращает `403 Forbidden` при недостатке прав.

## 8. Бизнес-правила

### 8.1. Смета

- Смета принадлежит одному объекту.
- В рамках одного объекта допускаются версии сметы.
- Новая версия сметы создается на основе предыдущей и сохраняет историю изменений.
- Сметные позиции автоматически пересчитывают итог сметы.
- После перевода сметы в `READY_FOR_PURCHASE` сметчик больше не может менять позиции.

### 8.2. Потребность в материалах

- Потребность по материалам агрегируется из всех сметных позиций конкретной сметы.
- Если один и тот же материал встречается в нескольких позициях, система суммирует количество.
- Агрегированная потребность используется как основа для формирования закупки.

### 8.3. Закупка

- Закупку можно создать только для сметы в статусе `READY_FOR_PURCHASE`.
- После создания закупки смета автоматически получает статус `IN_PURCHASE`.
- Позиции закупки предзаполняются на основании агрегированной потребности.
- Руководитель или администратор могут утверждать закупку.
- Для каждой позиции закупки можно сохранить несколько предложений поставщиков.
- По позиции может быть выбран только один активный поставщик-победитель.
- Система показывает отклонение фактической стоимости от плановой по каждой позиции и по закупке в целом.

### 8.4. Согласование

- Закупка может быть отправлена на согласование со статусом `SUBMITTED`.
- Руководитель может либо утвердить закупку, либо вернуть ее на доработку комментарием.
- Комментарии согласования хранятся в истории и отображаются в карточке закупки.

### 8.5. Объект

- Статус объекта отражает общий ход работы.
- При наличии активной закупки объект может быть переведен в `PURCHASE_IN_PROGRESS`.
- После завершения закупки и закрытия сметы объект может быть переведен в `COMPLETED`.

### 8.6. Журнал действий

- Система фиксирует создание и изменение ключевых сущностей.
- В журнал пишутся действия по сметам, закупкам, пользователям и материалам.
- Пользователь может просматривать историю по карточке сметы и закупки.

## 9. Пользовательские сценарии

### 9.1. Сметчик

1. Авторизуется в системе.
2. Открывает объект.
3. Создает смету.
4. Добавляет сметные позиции с выбором материалов, количества и цены.
5. Просматривает итог сметы и агрегированную потребность.
6. Переводит смету в статус `READY_FOR_PURCHASE`.

### 9.2. Снабженец

1. Авторизуется в системе.
2. Открывает смету со статусом `READY_FOR_PURCHASE`.
3. Создает закупку на основании потребности.
4. Запрашивает или вручную заносит предложения поставщиков.
5. Сравнивает предложения по цене и сроку поставки.
6. Выбирает лучшее предложение для каждой позиции.
7. Корректирует цены поставщика и комментарии.
8. Отправляет закупку на согласование.
9. Переводит закупку в рабочие статусы после утверждения.

### 9.3. Руководитель

1. Авторизуется в системе.
2. Просматривает дашборд и ключевые показатели по объектам.
3. Открывает закупку.
4. Проверяет плановую сумму, фактические значения и выбранных поставщиков.
5. Просматривает комментарии и историю изменений.
6. Утверждает закупку или возвращает на доработку.

### 9.4. Администратор

1. Авторизуется в системе.
2. Управляет пользователями.
3. Поддерживает справочник материалов.
4. Поддерживает справочник поставщиков.
5. Контролирует полноту тестовых данных и доступов.

## 10. Функциональные требования

### 10.1. Аутентификация

Система должна:

- предоставлять вход по email и паролю;
- предоставлять самостоятельную регистрацию нового пользователя;
- выдавать JWT;
- возвращать профиль текущего пользователя;
- отклонять неверные учетные данные с понятной ошибкой на русском языке.

### 10.2. Управление объектами

Система должна:

- отображать список объектов;
- позволять создавать и редактировать объекты пользователям с достаточными правами;
- показывать карточку объекта с привязанными сметами и закупками.

### 10.3. Управление материалами

Система должна:

- отображать каталог материалов с фильтрацией;
- позволять администратору создавать и редактировать материалы;
- хранить единицу измерения, артикул и ориентировочную цену.

### 10.4. Управление поставщиками

Система должна:

- отображать список поставщиков;
- позволять администратору создавать и редактировать поставщиков;
- хранить контактные данные и условную оценку надежности поставщика.

### 10.5. Управление сметами

Система должна:

- создавать сметы по объекту;
- создавать новую версию сметы на основе существующей;
- показывать номер версии и историю версий;
- добавлять и редактировать позиции сметы;
- автоматически считать сумму по позиции и общую сумму сметы;
- строить сводную потребность по материалам;
- переводить смету в статус готовности к закупке.

### 10.6. Управление закупками

Система должна:

- создавать закупку по смете;
- переносить агрегированные материалы в закупочные позиции;
- позволять заносить несколько предложений поставщиков по каждой позиции;
- подсвечивать наиболее выгодное предложение;
- хранить плановые и фактические суммы;
- менять статусы закупки по ролевой модели;
- отображать отклонение фактической суммы от плановой;
- поддерживать комментарии согласования;
- позволять экспортировать закупку в печатную форму.

### 10.7. Управление пользователями

Система должна:

- отображать список пользователей для `ADMIN`;
- позволять создавать тестовых и рабочих пользователей;
- изменять роль и активность пользователя.

### 10.8. Дашборд

Система должна отображать:

- количество объектов по статусам;
- количество смет по статусам;
- количество закупок по статусам;
- общую плановую стоимость по активным сметам;
- общую плановую стоимость по активным закупкам;
- общую фактическую стоимость по завершенным закупкам;
- суммарное отклонение план/факт;
- топ материалов по стоимости.

### 10.9. Журнал действий и экспорт

Система должна:

- сохранять историю действий по ключевым сущностям;
- показывать журнал в карточках сметы и закупки;
- предоставлять экспорт сметы и закупки в печатную форму для сохранения в PDF через браузер.

## 11. Нефункциональные требования

- Интерфейс на русском языке.
- Адаптивность для desktop и mobile.
- Современный визуальный стиль без шаблонной верстки.
- Валидация форм на клиенте и сервере.
- Чистая архитектура и читаемая структура кода.
- DTO для API-запросов и ответов.
- Корректные HTTP-статусы.
- Идемпотентное сидирование.
- Пароли хранятся только в виде BCrypt-хеша.

## 12. API-контракты

Все ответы и ошибки должны быть в JSON.

### 12.1. Auth

#### `POST /api/auth/login`

Запрос:

```json
{
  "email": "admin@santehmontazh.local",
  "password": "secret"
}
```

Ответ:

```json
{
  "token": "jwt-token",
  "user": {
    "id": 1,
    "fullName": "Администратор",
    "email": "admin@santehmontazh.local",
    "role": "ADMIN"
  }
}
```

#### `GET /api/auth/me`

Ответ:

```json
{
  "id": 1,
  "fullName": "Администратор",
  "email": "admin@santehmontazh.local",
  "role": "ADMIN"
}
```

#### `POST /api/auth/register`

Запрос:

```json
{
  "fullName": "Иван Петров",
  "email": "ivan.petrov@santehmontazh.local",
  "password": "User123!"
}
```

Ответ:

```json
{
  "token": "jwt-token",
  "user": {
    "id": 5,
    "fullName": "Иван Петров",
    "email": "ivan.petrov@santehmontazh.local",
    "role": "ESTIMATOR"
  }
}
```

Правило MVP:

- самостоятельная регистрация создает пользователя с ролью `ESTIMATOR`;
- изменение роли выполняется администратором.

Добавляет предложение поставщика. Доступ: `ADMIN`, `PURCHASER`.

#### `POST /api/purchase-items/{itemId}/offers/{offerId}/select`

Выбирает предложение поставщика. Доступ: `ADMIN`, `PURCHASER`.

#### `POST /api/purchases/{id}/submit`

Переводит закупку в `SUBMITTED`. Доступ: `ADMIN`, `PURCHASER`.

#### `POST /api/purchases/{id}/approve`

Переводит закупку в `APPROVED`. Доступ: `ADMIN`, `MANAGER`.

#### `POST /api/purchases/{id}/return-for-revision`

Возвращает закупку на доработку с комментарием. Доступ: `ADMIN`, `MANAGER`.

#### `POST /api/purchases/{id}/order`

Переводит закупку в `ORDERED`. Доступ: `ADMIN`, `PURCHASER`.

#### `POST /api/purchases/{id}/receive`

Переводит закупку в `RECEIVED`. Доступ: `ADMIN`, `PURCHASER`.

#### `GET /api/purchases/{id}/comments`

Возвращает комментарии согласования.

#### `POST /api/purchases/{id}/comments`

Добавляет комментарий к закупке.

#### `GET /api/purchases/{id}/print`

Возвращает печатное представление закупки.

### 12.7. Users

#### `GET /api/users`

Возвращает список пользователей. Доступ: `ADMIN`.

#### `POST /api/users`

#### `PUT /api/users/{id}`

Обновляет пользователя. Доступ: `ADMIN`.

### 12.8. Dashboard

#### `GET /api/dashboard/summary`

Возвращает агрегированные показатели для главной страницы.

#### `GET /api/dashboard/deviations`

Возвращает аналитику по отклонениям план/факт.

### 12.9. Audit

#### `GET /api/audit`

#### `GET /api/audit/entity/{entityType}/{entityId}`

Возвращает историю по конкретной сущности.

## 13. DTO и валидация

Минимальные правила:

- email валидируется как email;
- пароль логина обязателен;
- `fullName` обязателен при регистрации;
- пароль регистрации должен содержать не менее 8 символов;
- название объекта обязательно и не пустое;
- название материала обязательно;
- количество и цена в смете не могут быть отрицательными или нулевыми;
- закупочные количества и цены не могут быть отрицательными;
- запрещены переходы в недопустимые статусы.

## 14. Структура Web UI

### 14.1. Публичные страницы

- `/login` - страница входа.
- `/register` - страница регистрации.

### 14.2. Защищенные страницы

- `/dashboard` - дашборд;
- `/projects` - список объектов;
- `/projects/:id` - карточка объекта;
- `/materials` - каталог материалов;
- `/suppliers` - справочник поставщиков;
- `/estimates` - список смет;
- `/estimates/:id` - карточка сметы;
- `/purchases` - список закупок;
- `/purchases/:id` - карточка закупки;
- `/reports/deviations` - аналитика план/факт;
- `/admin/users` - управление пользователями, только для `ADMIN`.

### 14.3. UI-ограничения

- Неавторизованный пользователь всегда перенаправляется на `/login`.
- `ADMIN` видит все разделы.
- `ESTIMATOR` не видит раздел управления пользователями и действия по созданию закупки.
- `ESTIMATOR` видит версии смет и журнал изменений по своим расчетам.
- `PURCHASER` не видит кнопки редактирования сметы.
- `PURCHASER` видит блок сравнения предложений поставщиков.
- `MANAGER` видит аналитические и просмотровые страницы, но не видит кнопки редактирования смет и материалов.

## 15. Seed-данные

Должны быть подготовлены данные в `product-api/seed-data/`:

- `material-categories.json`
- `materials.json`
- `suppliers.json`
- `projects.json`
- `estimates.json`
- `estimate-items.json`
- `purchases.json`
- `purchase-items.json`

Требования к тестовым данным:

- не менее 3 объектов;
- не менее 12 материалов;
- не менее 5 поставщиков;
- минимум по одной смете на каждый активный объект;
- минимум одна смета в статусе `READY_FOR_PURCHASE`;
- минимум одна закупка в статусе `SUBMITTED` или `APPROVED`;
- минимум по 2 предложения поставщиков для нескольких закупочных позиций;
- данные должны быть реалистичными для монтажных и сантехнических работ.

## 19. Критерии приемки

Проект считается готовым, если:

1. `docker compose up -d --build` поднимает PostgreSQL и API без ручных правок.
2. `product-api` применяет миграции Flyway автоматически.
3. Seed-данные загружаются автоматически и повторный запуск не создает дубликатов.
4. `product-api/users.txt` создается автоматически и пригоден для Playwright.
5. `npm run dev` в `product-web` запускает UI без критических ошибок.
6. Пользователь может войти в систему и получить доступ только к разрешенным страницам и действиям.
7. Смета корректно считает суммы позиций и общий итог.
8. Новая версия сметы сохраняет историю и не теряет предыдущие данные.
9. Закупка создается на основании агрегированной потребности по смете.
10. Система поддерживает несколько предложений поставщиков и выбор оптимального варианта.
11. Плановая и фактическая стоимость сравниваются корректно.
12. Ролевые ограничения совпадают в backend и frontend.
13. `npx playwright test` проходит успешно.
14. Скриншоты появляются в `product-web/artifacts/screenshots/`.
15. Исходный код закоммичен и отправлен в GitHub-репозиторий организации `diplomas-2026`.

## 20. Решения для дальнейшей реализации

Принятые технические решения:

- Архитектура API: controller -> service -> repository -> entity/dto/security/seed.
- JWT хранится на frontend в `localStorage` для MVP.
- Запросы frontend выполняются через централизованный API-клиент.
- Основной доменный поток: объект -> смета -> потребность -> закупка -> утверждение.
- Расширенный доменный поток: объект -> версия сметы -> потребность -> закупка -> предложения поставщиков -> согласование -> план/факт анализ.
- Основной визуальный акцент в UI: современная производственная B2B-система с чистой типографикой, контрастной навигацией и информативными карточками показателей.
